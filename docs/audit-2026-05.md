# Scheduling Workbench Audit (2026-05-06)

This audit precedes any deletion or schema change for the Scheduling Workbench
build. It is based on static inspection of `src/`, `supabase/`, `workflows/`,
`scripts/`, root config, env templates, and `.github/workflows`. Anything
labeled "remove" is gated on user confirmation.

The repo runs against **two Supabase projects**:

- **Main project** `saksjvmqyudkowxypoce` (`VITE_SUPABASE_URL`) — credentialing,
  agreements, licensure, profiles/roles, knowledge base, hiring pipeline,
  reimbursements, agencies. Client: `src/integrations/supabase/client.ts`.
- **ClinOps project** `bbquooftytwprllipcsb` (`VITE_CLINOPS_SUPABASE_URL`) —
  providers, scheduling submissions, shift recommendations, demand forecast,
  state targets, utilization, SLA, coverage. Client:
  `src/integrations/supabase/clinopsClient.ts`.

The Workbench is anchored to the ClinOps project. The main project stays for
the Tools nav (credentialing, hiring, reimbursements, etc.).

## 6. Pipeline shifts

### 6.1 Jotform ingest: PUSH replaces PULL

- Current: `sync-jotform-submissions` (Deno) polls Jotform on a cadence,
  writing `schedule_submissions` rows with `parsed_shifts` JSON.
- Target (per brief §5.1): Jotform webhook → new edge function
  `jotform-webhook` (Deno). Parses `shift_type` from the form field, matches
  by Vitable email, writes `schedule_submissions` (header) + N
  `shift_submissions` rows, sets `is_edit_of_id` if duplicate `(email,
  month)` exists, writes `unmatched_submissions` on email mismatch, triggers
  recommendation regenerate.
- Action: build new function alongside the poller. Verify with a real
  submission. Then disable the GitHub Actions cron and the poller.

### 6.2 Recommendation engine: rewrite as two-pass

- Current: `evaluate-schedule-submissions` + `emit-shift-recommendations`
  produce `shift_recommendations` rows tied to legacy submission shape.
- Target (per brief §8.2): two-pass engine writing `proposed_shifts` and
  `activation_recommendations`, with conflict flags. Greedy fill, no
  optimization in v1.
- Action: build new edge function `recommend-schedule` (or rename existing).
  Keep legacy function reachable until the new one is verified.

## 8. Risks / open questions

1. **Cross-project schema split.** `provider_state_status` lives on the main
   project, but the recommendation engine on the ClinOps project needs it.
   Options: (a) materialize a synced view on ClinOps; (b) run the engine on
   the main project. Recommendation: (a), with a daily refresh from a small
   `import-provider-state-status` edge function. Confirm before Step 2.
2. **Existing `shift_recommendations` consumers.** `useShiftRecommendations`
   reads/writes this table. Plan: keep the hook reading from the legacy
   table during transition, then point at `proposed_shifts` once the new
   engine populates it.
3. **`KnowledgeBase` decision.** The Knowledge Base page is the main remaining
   `notion_link` user surface and isn't part of Workbench. Move to `_legacy`
   and drop `notion_url` column, or keep the page and just retire the import
   button? Brief implies full removal. Confirm before deletion.
4. **Hiring `notion_page_id`.** Column is unused by Workbench but visible on
   `HiringPipelinePage`. Drop column outright vs. nullify and ignore?
   Confirm before migration.
5. **Legacy poller retention window.** Keep `sync-jotform-submissions` as a
   safety net for one month after webhook is verified, then retire. Confirm
   timing.
6. **Workbench tables on main project, scheduling source data on ClinOps
   project.** The schema migration `20260505120000` placed the new Workbench
   output tables on the main project, while `schedule_submissions`,
   `demand_forecast`, `state_demand_targets`, `providers`, and
   `shift_recommendations` live on ClinOps. The Workbench UI and engine will
   need to read/write across both. Recommended bridge: a thin sync that
   mirrors `provider_state_status` and the relevant `providers` columns into
   ClinOps. Alternative: move the new Workbench tables to ClinOps to
   consolidate. Confirm direction before Step 2.
